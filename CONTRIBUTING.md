# Contributing to Mac Cleaner

Thanks for helping. This project deletes files on people's machines, so it favors small, careful changes
over clever ones.

## Build and test

Requires macOS 14+ and a recent Xcode (Swift toolchain). There are no third-party dependencies, and none
should be added (including for argument parsing).

```sh
swift build                    # engine, app and CLI
swift test                     # all tests
swift build --product mac-cleaner && .build/debug/mac-cleaner scan   # try the CLI
MACCLEANER_MOCK=1 swift run MacCleaner                               # app with fake data (debug builds only)
scripts/build-app.sh --open    # release app bundle in dist/
```

Never test deletion against real data. Use `--dry-run`, the mock engine, or a temporary folder.

## Project layout

```
Sources/CleanerCore/   the engine: scanning, measuring, deleting. Models.swift is the contract.
Sources/MacCleaner/    the SwiftUI app. Talks to the engine only through CleanerEngine.
Sources/CLI/           the mac-cleaner command-line tool (hand-rolled argument parser, one file per command).
Tests/                 CleanerCoreTests (engine) and CLITests (parser, commands, with a fake engine).
Resources/             app icon (generated by scripts/make-icon.swift)
scripts/               build-app.sh, package.sh, install-cli.sh, update-cask.sh, make-icon.swift
packaging/             Homebrew cask template
VERSION                the single source of the version (also keep Sources/CLI/Version.swift in sync)
```

### The contract file

`Sources/CleanerCore/Models.swift` defines the types and the `CleanerEngine` protocol that the engine, the
app and the CLI share. Changing it affects all three (and the mock engine), so change it deliberately, update
every user of it in the same pull request, and give new protocol methods and initializer parameters defaults
so older conformers keep compiling. The JSON the CLI prints uses these Codable types; renaming a field is a
breaking change to that output.

## How to add a cleanup category safely

A category is a named group of paths (or commands) that the user can reclaim. Rules:

1. **Only rebuildable data is "safe".** If deleting it loses anything that cannot be re-downloaded,
   rebuilt or regenerated automatically (history, downloaded models you chose, backups, archives, the
   Trash), mark it `caution`.
2. **Verify the paths against the tool's own documentation**, not a blog post or a guess. Link the docs in
   the pull request. Prefer the tool's own cleanup command (`brew cleanup`, `docker system prune`) when it
   exists.
3. **Never touch credentials or configuration.** No tokens, keys, `config` files, dotfiles, databases that
   hold settings or accounts. If a folder mixes cache and config, target only the cache subfolder.
4. **Be as narrow as possible.** Name exact folders. No broad globs, no "everything under ~/.something".
5. **Say what deleting costs** in `detail` ("Re-downloaded on demand", "Next build is slower").
6. **Size honestly.** If only part of the measured size is freed (a shared store, a disk image), mark the
   size as an upper bound.
7. **Respect the engine's guards**: the home/temp allow-rule, protected folders and the session-age
   retention. Do not work around them.
8. **Hermetic tests.** Build a fake home in a temporary directory, point the category at it, and assert on
   what is found and what is removed. Tests must never read or write outside their temporary folder or
   depend on tools installed on the machine. A test never starts a real third-party program: fixtures
   have no tools installed unless the test injects a `FakeTools` box (see `Tests/CleanerCoreTests/TestSupport.swift`).
9. **Locations come from the tool's defaults, not from the environment.** If a tool lets an environment
   variable move its cache, add an entry to `OverrideScanner` (`Overrides.swift`) that says what the folder
   must contain and which entries may become items. Such items are always `caution`.
10. **Commands are exact shapes.** A new cleanup command needs its complete argv added to `CommandPolicy`
    (`Safety.swift`), with a strict pattern for any variable argument, and a test with shapes that must be
    refused. Anything read from disk (a name, an identifier) must match that pattern before it is used.

If you are unsure, open a "New cleanup target" issue first.

## Rules for engine code that touches the file system or runs programs

These exist because the app usually has Full Disk Access and deletes irreversibly. See SECURITY.md.

- **Deleting** goes through `Deleter` only. Never `FileManager.removeItem`, never a path-based walk, and
  never a program that is handed a path to delete (linked worktrees included: the folder is removed by
  `Deleter`, git only prunes the registration afterwards).
- **Every deleting entry point** starts with `LiveEngine.begin` and ends with `finish`. `begin` refuses when
  the home folder was relocated or a protected path is invalid, and writes the "started" audit record
  before anything is touched.
- **"Protected" has two meanings; pick the right one.** `PathGuard.isProtected` answers "may this be
  deleted?" (hidden subtrees and the user's top-level folders). `PathGuard.isHidden` answers "may this be
  listed, measured or walked into?" (hidden subtrees only). Scans and read tools use `isHidden`.
- **Fail closed.** A git command that fails or times out, a folder that cannot be read, a bound that is hit:
  each must end in "not offered" / "not backed up" / "in use", never in the permissive answer.
- **Listing things to delete** goes through `env.expandPattern` / `SafeGlob`, which refuse symlinked
  folders and, in shared temp areas, anything the user does not own.
- **git** is run only through `Git.open` (the layout check and the configuration audit) followed by
  `Git.run`. There is no other way to obtain the `GitRepo` value `Git.run` needs; do not add one. Files that
  say where a repository lives are parsed in `GitLayout` exactly the way git parses them; never trim or
  normalize them differently. The config allowlist (`GitConfigPolicy`) is per key: add a whole section only
  after checking every key git documents for it. New read-only git commands must pass
  `--ignore-submodules=all` where git would otherwise enter a submodule.
- **Other programs** are run through `env.run([...])`, which resolves the tool with the ownership checks and
  gives it the constructed environment. Do not read `ProcessInfo.processInfo.environment` to build a child
  environment, and do not add a variable to it without a reason written next to it.
- The mock engine and every `MACCLEANER_*` hook are inside `#if DEBUG`. Keep it that way: an environment
  variable must not change what a release build does.

## CLI changes

- Keep the parser strict: unknown flags are usage errors (exit 2) with a hint.
- Read commands must support `--json` and print nothing but JSON on stdout; progress goes to stderr and only
  on a TTY.
- Anything that deletes must support `--dry-run`, list what it will do, and refuse to run without a
  terminal unless `-y` is passed.
- Commands are tested with the `FakeEngine` in `Tests/CLITests`; add a test for each new flag.

## Pull requests

- Keep them focused; describe what and why. Fill in the template.
- `swift build` and `swift test` must pass with no new warnings.
- Add a line to `CHANGELOG.md` under *Unreleased* for anything user-visible.
- Releases: bump `VERSION` and `Sources/CLI/Version.swift`, move the changelog section, tag `vX.Y.Z`. The
  release workflow checks that the tag matches `VERSION`, builds and tests in a job without secrets, then
  signs and packages in the `publish` job and creates a **draft** release. Look at the draft's assets and
  notes, then publish it by hand.
- A safety claim in `SECURITY.md`, the README or a tool description is part of the change: when the code
  changes what is true, change the text in the same pull request, and add or adjust the test named next to
  the property in `SECURITY.md`.

### One-time repository setup for releases (maintainer)

The signing and notarization secrets must not be repository secrets. Create a GitHub **Environment named
`release`** (Settings > Environments) and put them there (`MACOS_CERTIFICATE_P12`,
`MACOS_CERTIFICATE_PASSWORD`, `MACOS_CODESIGN_IDENTITY`, `NOTARY_KEY_P8`, `NOTARY_KEY_ID`,
`NOTARY_ISSUER_ID`). Then, on that environment:

1. *Deployment branches and tags*: "Selected branches and tags", with one rule of type **tag**: `v*`.
2. *Required reviewers*: yourself (or the maintainers). Every release run then waits for an approval before
   the `publish` job, the only job that can read the secrets, starts.
3. Delete the same secrets from the repository-level secrets if they were ever stored there.

Protect the tags as well (Settings > Rules > Rulesets: restrict creation of `v*` tags to maintainers). Without
steps 1 and 2 the environment protects nothing: the "tag is on `main`" step in the workflow is only a
convenience, because the workflow file is part of the commit being released.
