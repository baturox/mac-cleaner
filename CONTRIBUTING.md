# Contributing to Mac Cleaner

Thanks for helping. This project deletes files on people's machines, so it favors small, careful changes
over clever ones.

## Build and test

Requires macOS 14+ and a recent Xcode (Swift toolchain). There are no third-party dependencies, and none
should be added (including for argument parsing).

```sh
swift build                    # engine, app and CLI
swift test                     # all tests
swift build --product mac-cleaner && .build/debug/mac-cleaner scan   # try the CLI
MACCLEANER_MOCK=1 swift run MacCleaner                               # app with fake data
scripts/build-app.sh --open    # release app bundle in dist/
```

Never test deletion against real data. Use `--dry-run`, the mock engine, or a temporary folder.

## Project layout

```
Sources/CleanerCore/   the engine: scanning, measuring, deleting. Models.swift is the contract.
Sources/MacCleaner/    the SwiftUI app. Talks to the engine only through CleanerEngine.
Sources/CLI/           the mac-cleaner command-line tool (hand-rolled argument parser, one file per command).
Tests/                 CleanerCoreTests (engine) and CLITests (parser, commands, with a fake engine).
Resources/             app icon (generated by scripts/make-icon.swift)
scripts/               build-app.sh, package.sh, install-cli.sh, update-cask.sh, make-icon.swift
packaging/             Homebrew cask template
VERSION                the single source of the version (also keep Sources/CLI/Version.swift in sync)
```

### The contract file

`Sources/CleanerCore/Models.swift` defines the types and the `CleanerEngine` protocol that the engine, the
app and the CLI share. Changing it affects all three, so change it deliberately, in its own pull request,
with defaults for new protocol methods so older conformers keep compiling. The JSON the CLI prints uses
these Codable types; renaming a field is a breaking change to that output.

## How to add a cleanup category safely

A category is a named group of paths (or commands) that the user can reclaim. Rules:

1. **Only rebuildable data is "safe".** If deleting it loses anything that cannot be re-downloaded,
   rebuilt or regenerated automatically (history, downloaded models you chose, backups, archives, the
   Trash), mark it `caution`.
2. **Verify the paths against the tool's own documentation**, not a blog post or a guess. Link the docs in
   the pull request. Prefer the tool's own cleanup command (`brew cleanup`, `docker system prune`) when it
   exists.
3. **Never touch credentials or configuration.** No tokens, keys, `config` files, dotfiles, databases that
   hold settings or accounts. If a folder mixes cache and config, target only the cache subfolder.
4. **Be as narrow as possible.** Name exact folders. No broad globs, no "everything under ~/.something".
5. **Say what deleting costs** in `detail` ("Re-downloaded on demand", "Next build is slower").
6. **Size honestly.** If only part of the measured size is freed (a shared store, a disk image), mark the
   size as an upper bound.
7. **Respect the engine's guards**: the home/temp allow-rule, protected folders and the session-age
   retention. Do not work around them.
8. **Hermetic tests.** Build a fake home in a temporary directory, point the category at it, and assert on
   what is found and what is removed. Tests must never read or write outside their temporary folder or
   depend on tools installed on the machine.

If you are unsure, open a "New cleanup target" issue first.

## CLI changes

- Keep the parser strict: unknown flags are usage errors (exit 2) with a hint.
- Read commands must support `--json` and print nothing but JSON on stdout; progress goes to stderr and only
  on a TTY.
- Anything that deletes must support `--dry-run`, list what it will do, and refuse to run without a
  terminal unless `-y` is passed.
- Commands are tested with the `FakeEngine` in `Tests/CLITests`; add a test for each new flag.

## Pull requests

- Keep them focused; describe what and why. Fill in the template.
- `swift build` and `swift test` must pass with no new warnings.
- Add a line to `CHANGELOG.md` under *Unreleased* for anything user-visible.
- Releases: bump `VERSION` and `Sources/CLI/Version.swift`, move the changelog section, tag `vX.Y.Z`. The
  release workflow checks that the tag matches `VERSION`.
